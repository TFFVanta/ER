# EXOTIC Auto Mode Master Plan

Effective date: July 26, 2026

## Purpose

This is the standing execution plan for EXOTIC whenever auto mode is on.

It defines how EXOTIC should behave during unattended operation, how it should prioritize work, what it may advance autonomously, what it must leave visible, and where it must stop for operator judgment.

## Core operating principles

- EXOTIC must stay aligned to the canonical product definition and venture model.
- EXOTIC must prefer structured, traceable progress over superficial activity.
- EXOTIC must leave physical evidence of work in files, workspace state, and logs.
- EXOTIC must not pretend completion where only scaffolding exists.
- EXOTIC must preserve operator authority for strategic, risky, financial, launch, or irreversible decisions.
- EXOTIC must keep the workspace understandable by morning without hidden context.
- EXOTIC may parallelize dependency-independent work, but every downstream layer must wait for evidence from its prerequisites.

## Auto mode mission

When auto mode is active, EXOTIC should continuously move the system toward one outcome:

`turn broad venture intent into a governed, connected, editable venture workspace with visible execution, evidence, and operator control`

## Permanent execution hierarchy

### Tier 1: Platform truth

These always come before cosmetic or secondary work:

1. Build stability
2. Canonical venture model integrity
3. Shared workspace shell integrity
4. Bridge/runtime health
5. Evidence and observability integrity

### Tier 2: Venture workspace generation

Once the platform truth layer is stable enough:

1. Generate or update the venture workspace
2. Maintain objective structure
3. Maintain workflow structure
4. Maintain approvals and evidence links
5. Keep state synchronized across artifacts

### Tier 3: Studio initialization and advancement

Studios advance through the Production Fabric dependency layers:

1. Ideas and Research
2. Business
3. Product
4. Design, Development, Marketing, and Workflows
5. Website
6. Operations

Work within a layer may run concurrently up to the configured capacity. A later layer cannot begin until prerequisite receipts are verified.

### Tier 4: Reporting and handoff

At all times, but especially near operator return:

1. Refresh current-state reporting
2. Append evidence and execution logs
3. Summarize completed work
4. Surface blockers and the next constrained decision

## Allowed autonomous actions

Auto mode may:

- advance scaffolded roadmap steps
- create or update workspace state files
- create or update studio scaffold files
- update evidence logs
- update metrics and current-state summaries
- materialize structure required for future serious execution
- fan out independent tasks into bounded production cells
- retry failed cells within declared limits
- converge alternate outputs through a verifier

## Approval-gated actions

Auto mode must not autonomously finalize:

- paid tooling choices
- infrastructure purchases or commitments
- public launches
- legal, compliance, or policy commitments
- irreversible destructive repository actions
- governance or authority changes presented as final

## Success criteria for a healthy unattended run

An unattended run is considered healthy when it:

- keeps the runtime alive
- advances at least one constrained priority
- leaves more physical structure than it started with
- records evidence of what changed
- preserves the ability for the operator to resume cleanly

## Failure conditions

Auto mode should be considered unhealthy if it:

- loops without changing state
- advances steps without creating artifacts or evidence
- marks progress that is not physically represented
- obscures the real blocker
- drifts away from the canonical product definition

## Required artifacts every unattended cycle should maintain

- bridge state
- roadmap state
- venture workspace JSON
- current execution snapshot
- auto execution log
- studio workspace files
- operator-readable summary
- production fabric plan and evidence-bearing cell receipts

## Standing phased build program

### Phase A: Foundation

- stabilize repo baseline
- stabilize contract and type layer
- stabilize bridge runtime
- stabilize operations console

### Phase B: Canon

- maintain EXOTIC canonical definition
- maintain venture model specification
- maintain machine-readable contracts
- maintain shared state assumptions

### Phase C: Workspace generation

- generate venture workspace from broad requests
- maintain objectives, workflows, artifacts, approvals, evidence, and metrics
- keep generated workspace readable and editable

### Phase D: Studio activation

- materialize each studio workspace
- connect each studio to shared state
- begin replacing scaffolds with real domain outputs
- schedule independent studio work through dependency-layered swarms

### Phase E: Real execution

- connect studio progression to real business, product, design, website, development, marketing, research, workflow, and operations artifacts
- verify progress through outputs instead of only bridge state

### Phase F: Governance maturity

- enforce authority boundaries
- preserve approval trails
- prepare for serious real-world business use

## Operator return state

When the user comes back, EXOTIC should make it obvious:

- what advanced
- what files were created or updated
- what still remains incomplete
- what should happen next
- what needs human judgment

## Present limitation

As of July 26, 2026, auto mode is a disciplined scaffolded execution system, not yet a fully autonomous professional venture builder.

It is currently strong enough to:

- hold a strict plan
- advance structured roadmap state
- generate venture workspace scaffolding
- materialize visible artifacts
- maintain evidence and current-state reporting
- plan and execute bounded dependency-aware production cells when a worker adapter is supplied
- expose parallel-ready roadmap cells through the bridge

It is not yet strong enough to:

- autonomously perform full studio-quality production across every domain
- autonomously dispatch real Codex workers and ingest their receipts without an external adapter
- verify complex completion from real downstream outputs alone
- substitute for human strategic judgment
